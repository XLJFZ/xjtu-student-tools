# XJTU Student Tools

**西安交通大学学生工具集** —— 面向西安交通大学学生的非官方开源工具集合。

> **非官方项目。** 本仓库由学生个人维护，与西安交通大学官方无隶属、授权或合作关系。

在线入口：<https://xljfz.github.io/xjtu-student-tools/>

## 项目定位

本仓库是一个**门户 / 项目索引 / 使用入口**，不是 monorepo，也不包含任何工具的业务代码。

- 本仓库只负责：导航、项目介绍、文档入口与统一品牌
- 每个工具都拥有自己的独立仓库、独立 release 与独立版本号
- 本仓库不复制、不内联任何子项目的源码
- 本站不接收、不存储、不处理账号、密码、Cookie、Token 或统一身份认证凭据

### 课程表同步

状态：**可用**（<!-- @v:calendar -->v0.9.1<!-- @/v -->，<!-- @d:calendar -->2026-10-23<!-- @/d -->）

将 eHall「我的课表」解析为标准 iCalendar（`.ics`）：既能导出文件导入手机、电脑与其他日历应用，也能发布成一个订阅 URL，让日历客户端定期回源取最新。

- 仓库：<https://github.com/XLJFZ/xjtu-timetable-calendar>
- 使用说明：<https://xljfz.github.io/xjtu-timetable-calendar/>
- 逐次实际上课生成独立事件，事件标识稳定；在会回源的客户端上，改课表现为原地更新。停课与考试改期以已取消的状态下发，客户端是否照做各不相同
- 除课程外，产物还能带上考试安排（默认包含，可关）与学校发布过的校历全天事件（默认不带）
- 需要 Python 3.11+，并**自行配置官方校历与作息表**（工具刻意不内置猜测值）
- 登录在你的浏览器中亲自完成，凭据不经手门户与本项目
- 发布成订阅 URL 后，产物里有什么就是公开什么：带上考试时，考试名、时间、考场和座位号也在其中（考试项可单独关掉）
- 订阅 URL 有两条托管路，**推荐私有仓库 + 第三方静态托管**（例如 Cloudflare Pages）：那条路才把「知道地址才订得到」变成真的，代价是要多注册一个第三方账号，且国内可达性得自己在手机上先验一次；公开的 GitHub Pages 五分钟就能跑通，但任何人都能列出那个分支里的文件名，token 挡不住会翻仓库的人

### 思源学堂工具

状态：**可用**（<!-- @v:siyuan -->v1.7.1<!-- @/v -->，<!-- @d:siyuan -->2026-10-24<!-- @/d -->）

下载思源学堂 2.0 中当前账号有权访问的课件、作业与课程回放，按类型与章节归类整理到本地。

- 仓库：<https://github.com/XLJFZ/xjtu-siyuanxuetang-grab>
- 使用说明：<https://xljfz.github.io/xjtu-siyuanxuetang-grab/>
- 附件散在三类来源（活动附件数组、活动正文内嵌、直播回放地址），只读一类会漏；课件 PDF 几乎都在正文内嵌那一类
- 作业附件只是题目，「交什么、怎么交、什么时候截止」写在活动详情里 —— 所以每个作业 / 实验活动除附件外另存一份 `说明.md`，把截止时间、提交方式与平台原文要求一并留下（富文本按段落转纯文本，内容没变就不重写文件）
- 带断点续传、失败重试、大小与 SHA-256 校验、增量更新，以及先看清单不动文件的预览模式
- 三种用法：装成 Skill 交给编码助手、配套 Prompt、或按命令行跑 `scripts/` 里的脚本；需要 Python 3.8+，只有登录环节依赖浏览器自动化
- 登录态还有效时不再打开浏览器，只花一次接口探测的时间；`--check` 只探测、`--force` 强制重登
- 只访问当前账号本就有权访问的资源，不绕过统一身份认证；主要用于个人备份与离线整理，请遵守学校规定与课程资源版权要求
- 未发布到 PyPI，从仓库克隆或 Release 附件获取

## 为什么拆成多个仓库

- **生命周期不同**：各工具的开发、维护与停止计划互相独立
- **release 独立**：各自发布版本，不需要为门户统一版本号
- **issue 独立**：问题追踪归属到具体项目，避免混淆
- **权限边界清晰**：不同工具对账号、会话与数据的处理方式不同，分离仓库便于单独说明与审计
- **门户职责单一**：本仓库只负责聚合与导航

## 技术实现

纯静态站点，无框架、无构建步骤、无第三方依赖：

```text
index.html                    门户首页
assets/css/style.css          样式（CSS 变量 + prefers-color-scheme）
assets/images/                站点图标与 Open Graph 图片
scripts/sync_versions.py      版本号同步脚本（标准库，无依赖）
.github/workflows/            定时跑上面那个脚本，见下节
```

- 零 JavaScript：所有导航与折叠内容均使用原生 HTML 实现，禁用 JavaScript 后功能完整
- 不使用 CDN，不加载任何外部资源
- 响应式布局，支持桌面端与移动端
- 跟随系统浅色 / 深色模式

本地预览：直接双击打开 `index.html` 即可，无需任何环境准备。

## 版本号同步

子项目的**版本号与发布日期**由一个定时 workflow 刷新，不再靠人记得回来改：
`scripts/sync_versions.py` 从 PyPI（课程表工具）与 GitHub Releases（思源学堂工具）取现值，
只改写被注释标记包住的区间，区间外的文案一个字都不动。

```html
当前版本 <!-- @v:calendar -->v0.9.1<!-- @/v -->（<!-- @d:calendar -->2026-10-23<!-- @/d -->）。
```

- 开始标记带关键字（`@v:` 收版本号、`@d:` 收发布日期），闭合标记是 `@/v`、`@/d`；版本号写成 `v0.9.1` 这种形状，日期写成 `2026-10-23`；同一文件里可以出现多次
- 开始与闭合必须在**同一行**：脚本只认行内区间，所以正文里提到这套写法时若不成对出现，不会被误当成待替换内容
- 判据 fail-closed：任一来源取不到、版本形状非法、标记关键字不认识、或区间被清空，
  两份文件都不写、退出码 1；只有真的有变化时才产生提交
- 日期一律换算成北京日期再比：PyPI 与 GitHub 返回的是 UTC，而本项目文档写的发布日期是北京时间，
  实测 0.9.0 与 0.9.1 两次上传都落在 UTC 16 点后，不换算就会每天把正确的日期「改」回前一天
- **通路描述、默认值、安全说明这些要人判断的内容不在自动化范围内**，由脚本分级、workflow 开 issue 提醒人来改：
  - 每次改写都按 `旧值 → 新值` 分级：`patch`（补丁号）自己刷完就算；`minor`、`major` 会开一条 issue，因为这种跳法通常意味着多了通路或改了默认值，光刷数字不够
  - 另外两种是"数据本身有问题"的形状，同样开 issue：`inconsistent`（同一个 key 在 `index.html` 与 `README.md` 里写了不同数字，2026-10-23 那天门户三处版本号分两次才改齐就是这个形状）、`regress`（门户写的比上游还高）
  - 一个工具只留一条开放 issue：已有没关的就追加评论，不重复开
  - issue 正文里写明要复核哪两处、以及依据回上游哪里取；数字照刷，句子等人

手动跑一次（本地需显式指定代理）：

```bash
HTTPS_PROXY=http://127.0.0.1:7897 python scripts/sync_versions.py --check   # 只报告，不写盘
HTTPS_PROXY=http://127.0.0.1:7897 python scripts/sync_versions.py           # 真的改写
```

定时任务的三条边界：`schedule` 只在默认分支上跑；公共仓库连续 60 天无任何活动后定时任务会被自动停用（有活动即恢复）；高峰期可能被推迟，所以「每天」实际是「通常每天」。要立刻跟上就在 Actions 里手动 run workflow。

这套判据已经在 2026-10-23 用一次演练跑通：把课程表的标记临时写成 `v0.8.9`，手动触发一次
workflow_dispatch，bot 自己提交把三处刷回 `v0.9.1`，并开出「文案复核：课程表同步 v0.8.9 → v0.9.1（minor）」。
演练值这个价，因为它抓到一个平时看不见的问题：`actions/checkout` 默认把 HEAD 放在游离状态，
裸跑 `git push` 只在**真的有版本号要提交**那一次才 fatal——日常每天都是绿的，第一次发版才会红。
现在那一步显式推 `git push origin "HEAD:$GITHUB_REF_NAME"`。

## 部署

使用 GitHub Pages 的**分支部署**方式（Deploy from a branch）：`main` 分支根目录 —— 部署由 GitHub Pages 内置的构建流程完成，不依赖任何 workflow。

根目录的 `.nojekyll` 是一个空文件，用于显式关闭 Jekyll 处理，确保静态文件按原样提供服务。

仓库里唯一的 workflow 是 `.github/workflows/sync-versions.yml`（见上一节），它只写版本号与开复核 issue，不参与部署；权限用到 `contents: write` 与 `issues: write`，都走内置的 `GITHUB_TOKEN`，**仓库里不存任何 token**。Pages 在 `main` 有新提交后自行重建，实测延迟约 2 分钟。

## Security

**请勿在任何公开位置提交以下内容：**

- Password（账号密码）
- Cookie
- Token
- Session
- 临时下载 URL
- 身份认证响应

其他要求：

- 本站不要求输入西安交通大学账号或密码
- 使用各子项目时，请先阅读对应项目的安全说明与使用范围
- 所有工具都应尽量在用户本地处理认证信息与数据
- 如发现安全问题，请勿公开披露敏感信息，优先通过仓库提供的私密联系方式报告
